# YOLO11 特征激活可视化工作坊

用 **真实预训练权重**（`yolo11n.pt`）在浏览器里逐层查看 YOLO11 的特征激活。
不是示意图：网页里跑的是一次真正的 ONNX 前向传播，每一层的热力图都来自该次推理的真实张量。

技术栈：**Vite + React 19 + Three.js + onnxruntime-web（WASM）**。

---

## 快速开始

```powershell
npm install          # 会自动把 onnxruntime-web 的 wasm 运行时复制到 public/ort
npm run dev          # http://localhost:5173
```

想自己重新导出模型（需要仓库里的 Python 环境）：

```powershell
npm run export:onnx  # .venv312 里跑 tools/export_onnx.py --imgsz 320
npm run verify:onnx  # 与 torch 输出对比，验证导出正确
npm run export:graph # 解析 ONNX 计算图，生成网络拓扑 public/models/graph.json
```

## 它是怎么工作的

```
street.jpg ──letterbox(114灰边,320×320)──▶ Float32 NCHW ──▶ ONNX Runtime (wasm)
                                                              │
                          24 个图输出 + output0 ◀──────────────┘
                                    │
        ┌───────────────────────────┼────────────────────────────┐
   逐层统计/RMS 通道能量       检测解码 + NMS              可视化渲染
   （右侧统计面板）           （检测结果面板）       （2D 热力图 / 3D 堆叠）
```

一次前向大约 **180 ms**（CPU / wasm，4 线程），拿到 25 个张量。

### 模型契约

`tools/export_onnx.py` 把 YOLO11 的中间张量加进 ONNX 的 `graph.output`：

- 输入：`images` `[1, 3, 320, 320]` float32（动态维度）
- 输出：`output0` `[1, 84, 2100]`（4 个框坐标 + 80 类分数，DFL 已在导出时解码）
- 另外 23 个输出：`/model.0/act/Mul_output_0` … `/model.22/cv2/act/Mul_output_0`
- 附带 `images` 本身作为输出，方便直接查看预处理后的输入张量

`public/models/layers.json` 描述这 27 个阶段（input / pre / m0…m23 / output），
包含模块名、stride、所属分组和一段中文说明。

## 界面

- **左侧 流水线**：backbone / neck / head 分组的 27 个阶段。点选任意层，右侧条形长度表示该层激活的 RMS 能量（检测头 logits 量级过大，已排除在归一化之外）。
  多路输入的层（颈部 Concat、Detect）会标出来路提示 `← m11 + m6`，一眼看出这不是一条直线。
- **中间 视口**：四个视图
  - `2D 特征图`：单通道 / PCA 三通道合成 / 通道均值 / 最大值 / L2，可叠加原图、叠加检测框，鼠标悬停可读出**某个像素的真实激活值**，底部有色标图例与显示区间。
  - `通道网格`：按能量排序的前 12 个通道小图矩阵，一眼看出特征分化。
  - `3D 特征金字塔`：每一层的特征图作为一块切片，沿深度斜向堆成一摞，点击切片切换选中层。
  - `3D 通道堆叠`：把选中层能量最高的若干通道叠成多层「地形图」，**激活值直接做高度位移**，可调起伏幅度。
- **整屏 网络结构图**：`架构图`（默认，纵向按分辨率、横向按处理阶段，颈部是 U 形）/ `依赖图`（横排紧凑版）两种排布，见下一节。
- **整屏 层间关系**：`A/B 对比`（两块画布共用缩放、平移与探针，专治 Upsample / Concat 前后）与 `跳连拆解`（跨层跳连把哪一段通道搬到了哪一层，并用真实激活验证），见下面「层间关系」一节。
- **整屏 检测头解剖**：把 `output0` 拆回 2100 个锚点，讲清「特征图 → 锚点 → 分类分数 → 阈值 → NMS → 框」这条链路，见下面「检测头解剖」一节。
- **右侧 控制面板**：配色（viridis/inferno/turbo/ice/灰度/冷暖）、伽马、显示区间（百分位/minmax）、通道、堆叠间距、通道数量、置信度阈值与 NMS IoU。
- **右侧 统计面板**：选中层的均值/标准差/极值/RMS/正值占比，以及通道能量排行。

### 真实 vs. 推断

| 内容 | 来源 |
| --- | --- |
| 每层张量数值、形状、统计、热力图 | **真实** 权重前向结果 |
| 检测框、类别、置信度 | **真实** NMS 解码结果 |
| PCA / 通道能量 / 高斯起伏 | 对真实张量的后处理 |
| 层的语义说明（`layers.json` 的 `desc`） | 人工撰写，属解释性文字 |
| 结构图的连边（含 6 条跨层跳连） | **真实** ONNX 计算图自动提取，非人工绘制 |
| 结构图里节点落在哪一行哪一列 | 按 YOLO11 的模块语义手工归档（`ARCH_SLOTS`），属人工排布 |
| 锚点网格、类别概率热力图、NMS 抑制过程 | **真实** `output0` 的解码过程，与界面上的检测框同一份代码 |
| 层间关系里两块画布的图像与探针读数 | **真实** 一次前向的两层激活，坐标系统一在 letterbox 后的输入图上 |
| Concat 的通道归属（哪一段来自哪一层） | **真实** ONNX 算子的输入顺序（`graph.json` 连边顺序即算子输入顺序） |
| 段内 L2 能量占比、源层与目标层的逐通道差值 | 对真实张量的计算；差值为 0 可直接验证「Concat 只搬运、不计算」 |

## 网络结构图（真实拓扑）

左上角 **网络结构图** 按钮打开整屏的结构视图。它不是按 `layers.json` 顺序画的一条线，
而是 `tools/export_graph.py` 解析 `yolo11n_vis.onnx` 的 **581 个算子**、按 `/model.<N>/` 前缀
归并成 24 个模块，再统计每个模块真正吃进的外来张量，由此得到 **32 条连边**，其中
**6 条是跨层跳连**（排布参考了 `YOLOv11 架构.svg`，但节点与连边以 ONNX 为准）：

| 跳连 | 跨度 | 张量 | 含义 |
| --- | --- | --- | --- |
| m6 → m12 | 跨 6 层 | 128×20×20 | 骨干 P4 直接进颈部 Concat |
| m4 → m15 | 跨 11 层 | 128×40×40 | 骨干 P3 直接进颈部 Concat |
| m13 → m18 | 跨 5 层 | 128×20×20 | 颈部内部再融合 |
| m10 → m21 | 跨 11 层 | 256×10×10 | 骨干 SPPF/C2PSA 进颈部 Concat |
| m16 → m23 | 跨 7 层 | 64×40×40 | P3 特征直送 Detect |
| m19 → m23 | 跨 4 层 | 128×20×20 | P4 特征直送 Detect |

### 两种排布

右上角切换（默认 **架构图**）：

- **架构图** —— 与你给的 `YOLOv11 架构.svg` 同构：**纵向是分辨率，横向是处理阶段**。
  - 最左 `骨干 Backbone`：input / pre / m0…m10 一路向下，stride 逐级翻倍，左侧标出 P1/2 → P5/32 的尺度带。
  - 中间两列是颈部，按**真实方向**画成 U 形：`自顶向下 (FPN)` 由下往上（m11 Upsample → m16），
    `自底向上 (PAN)` 由上往下（m17 Conv s2 → m22 C3k2）。
  - 最右 `检测头 Head`：m23 Detect 同时接 P3 / P4 / P5 三路，再输出 decoded 张量。
  - 按算子类型上色（Conv 蓝 / C3k2 橙 / Concat 绿 / Upsample 粉 / SPPF 紫 / Detect 黄）。
  - **6 条跳连因此变成横线**：`m6→m12`、`m4→m15` 与骨干同高，是笔直的一横，
    一眼就能看出颈部 Concat 到底融了骨干哪一层的特征。
- **依赖图** —— 原来的紧凑排布：按最长路径深度横排、backbone / neck / head 分三行，适合快速纵览顺序。

校对方式：`ARCH_SLOTS` 把 26 个阶段手工归档到 4 列 × 6 条尺度带，
但连边仍全部来自 `graph.json`，两边可以逐条对上；
`npm run probe:structure` 会断言 `m6→m12`、`m4→m15` 在屏幕上确实画成了横线（`dy = 0`）。

交互方式：

- 滚轮缩放、拖背景平移、**拖节点自由摆位**（只改排布，不动数据）。
- 右上角 `架构图 / 依赖图` 切换排布，切换后自动重新适配窗口。
- 点节点 = 选中该层：图上蓝色高亮它的全部上游依赖、绿色高亮下游流向，其余压暗。
- 右侧详情给出张量形状、数值统计、可点击的「输入来自 / 输出流向」列表，以及 6 条跳连清单一键跳转。
- 「回中间查看这一层的数据」关掉浮层，中间视图就停在刚选的那层上，左侧列表同步选中。
- 详情里的 **PCA / 单通道 / 均值** 可换预览图的通道合成方式（与右侧控制面板的「切片配色」是同一个设置）。
- 缩放到 62% 以上才显示模块名与形状，32% 以上才显示节点编号，避免缩小时糊成一团。

> 拓扑是从 ONNX 图里算出来的，不是照着论文画的；模块归属、`span`、连边都可复现（`npm run export:graph`）。

## 检测头解剖（特征图 → 锚点 → 分类 → NMS）

顶栏 **检测头解剖** 按钮打开整屏视图（选中 `m23` 或 `output` 时，中间视口的提示条里也有同一个入口）。
它只讲一件事：**检测头是怎么把三张特征图变成一个检测框列表的**。
数据全部来自同一次前向的 `output0`（`[1, 84, 2100]`），和中间视图里显示的框共用同一份解码代码
（`src/model/detect.js` 的 `decodeCandidates` + `nmsTrace`）—— 所以改阈值只重算解码，不会重跑网络。

左边是四个步骤，中间是那块 2100 个格点的画布，右边是当前选中格点的真实读数：

- **① 特征图 → 分支**：颈部交给检测头的三路特征图（`m16` 64×40×40 / `m19` 128×20×20 / `m22` 256×10×10）
  各自独立地投影出「框回归 64 通道（4 个方向 × 16 个 DFL bin）+ 类别分数 80 通道」，拼起来就是每格 84 个数。
  右侧会拿这张图里**分数最高的那个格点**举例，给出它解出的 `cx, cy, w, h` 和判成的类。
- **② 锚点网格**：2100 个格点 = **1600（P3, 40×40）+ 400（P4, 20×20）+ 100（P5, 10×10）**，
  按 stride 铺回 letterbox 图像上，每个格子正好是图像上 `stride × stride` 像素的一块。
  着色可在「每格最高类分数」与「指定类概率」之间切换（点右侧类别排行即换），点的每一格都会读出
  它的 4 个框回归量、80 个类别分数，以及它在 NMS 里的最终命运。
- **③ 置信度筛选**：分数 ≥ 阈值的格点成为候选。这里能直接看到「一个目标周围的很多格子同时响应、
  框还互相叠着」—— 这正是下一步要处理的问题。
- **④ NMS 抑制**：逐类贪心抑制的回放。绿色 = 保留，蓝色 = 当前正在判定的框，红色虚线 = 被它压掉的重复框；
  可以单步，也可以自动播放，右侧日志记录每一步保留了谁、压掉了几个。

底部漏斗把整条链路串起来：`3 张特征图 → 2100 个锚点 × 84 个数 → N 个候选 → M 个框`。
`npm run probe:head` 会端到端跑一遍：逐阶段切换、点格点、单步与自动播放 NMS、从检测头那层再进来一次。

> 格点序号与网格坐标的对应（`output0` 按 P3 → P4 → P5 拼接、同尺度内行优先展平）不是猜的：
> 它满足一条可断言的不变量 —— `cx = 格点中心 + (右距 − 左距) / 2`，而左右距都落在框内，
> 所以**框中心偏离格点中心不会超过半个框宽**。`npm run probe:head` 会逐尺度点若干格点、
> 用右侧面板上的真实读数去验这条不变量（当前示例图 12/12 通过）。拼接顺序或展平方式一旦搞错，
> 几乎必然被打破。

## 层间关系（A/B 对比 + 跳连拆解）

顶栏 **层间关系** 按钮打开整屏视图。它补的是前面所有视图都缺的那条轴：**层与层之间发生了什么**。
单层视图回答「这一层长什么样」，这一页回答「两层之间是放大、拼接，还是原样搬运」。
入口有三个：顶栏按钮、结构图右侧每条跳连旁边的「拆解」按钮、以及选中颈部拼接层时中间视口顶部提示条里的「拆开看」。

**A/B 对比**：同一张图、同一次前向，左右两块画布，缩放 / 平移 / 探针全部联动，可任选两层。
坐标系固定在 letterbox 之后的输入图空间，所以 `m10`（256×10×10）与 `m11`（256×20×20）并排时，
看到的是**同一块图像区域的两套采样密度**：鼠标停在一处，两块画布各自报出自己格点的真实激活值，
格点下标正好差 2 倍。左侧「常见对照」里的 12 组组合是从真实连边推出来的
（`Upsample 前后` / `Concat 前后（第 1 路）` / `跳连汇入 Concat` / `浅层 vs 深层` / `骨干 vs 颈部输出`）。

**跳连拆解**：点一条跨层跳连（如 `m6 → m12`），并排显示源层与汇入层，并给出**通道归属** ——
`m12` 的 384 个通道里 `0–255` 来自 `m11`（上采样后的深层）、`256–383` 来自骨干 `m6`（浅层细节），
33% 的通道是这条跳连搬过来的；右侧同时给出每一段的 **L2 能量占比**（`m6` 这一段占 39.3%），
通道数与能量并排，才看得出「多」和「强」不是一回事。目标显示范围切到「只看这一段」时，
右图就是源层那一摞通道的均值图，与左图逐点一致。

> 通道归属不是猜的：`graph.json` 的连边顺序**就是** ONNX 算子的输入顺序（`tools/export_graph.py`
> 按 `node.input` 去重保序生成），切分点直接由各路通道数累加得到。
> 而且这条结论可以被验证 —— 源层各通道与目标层对应通道**逐元素差值必须为 0**（Concat 只搬运、不计算）。
> `npm run probe:relations` 会检查这个差值，当前示例图上为 `0.000000`；
> 它同时验证探针不变量（同一图像位置在两层里的格点下标相差整数倍）与 Upsample 的数值不变性（4/4 通过）。

底部摘要条把 `A → B` 的形状变化摊开（空间分辨率 / 通道数 / 张量元素，以及放大还是不变），
四个颈部 Concat（`m12` / `m15` / `m18` / `m21`）都拆得出段；`m23`（Detect）的三路输入空间尺寸不同，
属于并行分支而不是通道拼接，这时页面会明说拆不开，而不是硬凑一张图。

## 已知限制

- 只支持 CPU（wasm）执行；WebGPU 后端未启用。
- 模型按 `imgsz=320` 导出，位置编码与锚点数量（2100）与之绑定；换尺寸需重新导出。
- 3D 金字塔的「单通道」配色对所有层使用同一个通道索引，不同层的通道语义并不对齐，仅作参考。
- `public/ort` 下的 wasm 从本地加载（CDN 不可达），构建产物因此偏大，属预期行为。
- 结构图的模块划分依赖导出时张量名的 `/model.<N>/` 前缀；若改用别的方式导出 ONNX，需要重跑 `npm run export:graph` 校对。
- 结构图里 `rank`（深度层级）由最长路径松弛算出，仅用于排序与标注，不代表计算依赖的先后约束。
- 架构图的「哪个节点落在第几列第几行」是人工归档在 `ARCH_SLOTS` 里的（依据 YOLO11 的模块语义），
  连边则完全来自 ONNX。若换一份骨干/颈部结构，需要同步改这张表；表里的 26 个阶段会被逐一放到画布上，
  缺一个就会在图上少一块。
- 检测头解剖里的框回归量是**导出时就已经解码过的** `cx, cy, w, h`，所以看不到 16 个 DFL bin 的分布；
  想看 bin 分布需要在 `tools/export_onnx.py` 里把 `cv2` 的 64 通道输出也加进 `graph.output` 再重新导出。
- 检测头解剖的「候选」按分数截断在 300 个（与解码时的 `preNmsTop` 一致），阈值调得很低时不会显示全部格点。
- 层间关系不做通道配对意义上的「差异图」：两层的通道语义并不一一对应，逐点相减只能得到一张好看但没有意义的图。
  能诚实地做的对比是「同一块图像区域的格点读数」「同一段通道的逐元素差值」和「段内能量占比」。
- 层间关系的通道归属依赖 `graph.json` 的连边顺序；重新导出 ONNX 后需要重跑 `npm run export:graph` 校对。
- 「只看来自源层的那一段」只在该层确实按通道拼接时成立（各路空间尺寸相同、通道数之和等于输出通道数）；
  对 `m23`（Detect）这种三路输入尺寸不同的层会明确显示「拆不开」。
